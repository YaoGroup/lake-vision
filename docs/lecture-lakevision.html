01The problem

Every melt season, thousands of lakes form on the surface of the Greenland Ice Sheet. Some quietly refreeze. Others drain — and how they drain matters: a lake that hydrofractures through a kilometer of ice delivers its water (and a new conduit) to the bed in hours, lubricating ice flow, while a lake that spills laterally into a downstream channel does something entirely different to the system. Classifying drainage style at scale, from satellite record alone, is what this repo is for.

The unit of prediction is one lake, one melt season. The model sees a summer-long sequence of Sentinel-2 image tiles centered on the lake, plus the lake's water-area time series, and outputs one of five classes:

IndexCodeMeaningCount (combined CW)
0NDNo drainage — fills, persists or refreezes236
1HFHydrofracture — rapid drainage through a new fracture279
2MDMoulin drainage — drains via an existing moulin242
3LDLateral drainage — overflows into surface channels580
4CDCrevasse drainage — drains into a crevasse field342

The labeled dataset covers the CW (central-west) IMBIE drainage basin: 679 lakes from 2018 and 1,000 from 2019, hand-labeled in the sat-tile-stack GUI and published as the ESSD data deposit. Labels are strings (ND…CD) in per-year CSVs; the training code maps them to integers 0–4. Note the class imbalance — LD is 2.5× ND — which is why training weights the loss by inverse class frequency.

02The data workflow

Two repos share the work. sat-tile-stack (a sibling repo) talks to the satellite archive: it queries Sentinel-2 L2A, cuts 512×512 tiles at 10 m/px around each lake, and writes one raw NetCDF stack per lake per season. lake-vision (this repo) takes it from there: it fuses those stacks with lake polygons and water-area series from Dunmire et al. (2025) into per-lake composites, trains on them, and runs inference.

The composite file

A composite is one lake-season in one self-contained NetCDF file, named {lake_id}.nc (e.g. CW2019_1579.nc). The schema, from an actual file:

dimensions:   time = 153,  channel = 4,  y = 512,  x = 512
variables:
  imagery     float32  (time, channel, y, x)   # channel = [red, green, blue, mask]
                                               # reflectance in raw DN (÷10000 ≈ [0,1]); NaN where no data
  water_area  float64  (time,)                 # fraction of lake polygon that is water, 0–1
                                               # from Dunmire S2_water, ffill/bfill-filled
  time        int64    (time,)                 # observation timestamps
attributes:   lake_id, year, description, source_imagery

Newer stacks in the canonical stacks_v2 deposit carry more: 6-band reflectance (adds NIR + two SWIR), a static lake_boundary polygon mask, a dynamic water_mask_ndwi, and p_water. LakeDataset auto-detects both formats. What the deposit still lacks is the cloudy_seq_* per-frame usefulness flag (see docs/CV_GRID.md for the plan to add it).

Splits are files, not code

Train/val/test membership is not recomputed per run. engine/training/split_fixed.py generated them once — seeded (42), class-stratified, with the train list ordered so that every prefix train_ids[:N] is itself stratified (that's what makes the learning-curve runs nested) — and the resulting JSON files are committed under splits/:

SplitTrainValTestDesign
splits/essd_CW/1,1753361682018+2019 combined, 70/20/10
splits/essd_CW_crossyear/800200679train+val on 2019, test = all of 2018

The cross-year split is the honest one: it asks whether a model trained on one season generalizes to another. The combined split is easier — and note that because lake IDs are per-year (CW2018_* vs CW2019_*), the same physical lake can appear in train (as its 2018 self) and test (as its 2019 self). Keep that in mind when comparing the two baselines' numbers.

03From file to tensor

lakevision/data/datasets.py::LakeDataset is where a NetCDF file becomes model input. Per sample (__getitem__), it returns five things: img_seq [T,C,H,W], area_seq [T,1], cloudy_seq [T,1], an integer label, and the lake_id string. Four transformations happen on the way:

1. Channel selection. Only the requested channels are read — a hyperslab read per channel index, so unrequested bands are never decompressed. Both file formats are auto-detected: composite imagery with a string channel coordinate, and SDR reflectance whose band names live in the band_name char array (B04/B03/B02/B08/B11/B12 → red/green/blue/nir/swir16/swir22). The baseline loads [red, green, blue, mask]. Band flags on the dataset must match the flags on the model; nothing asserts this on main (a channel-count assert exists only on feature/cache-data).

2. Temporal windowing. The sequence is cut to seq_len=153 frames centered on the water-area peak — the argmax of a NaN-filled copy of water_area — clamped at the season's edges. Since composites are exactly 153 frames long, the window is currently the whole series; the machinery matters when seq_len shrinks or stacks lengthen.

3. Normalization. Imagery: reflectance channels are divided by 10,000 and clipped to [0,1]; the mask channel is passed through untouched; NaNs become 0. (A per-band mean/std path exists behind band_stats, but no stats file has ever been computed — it's a planned CV-grid axis, not a used feature.) Area: min-max normalized per sample, so every lake's curve spans exactly [0,1] regardless of lake size. Inference must mirror both normalizations exactly; run_inference.py and predict_lakes.py do, as of August 2026 (§08).

4. Augmentation (train only, opt-in). Satellite tiles have no canonical orientation, so the natural augmentation group is D4 — the 8 symmetries of a square — applied identically to every frame so temporal coherence survives:

Why the dataloader is the whole performance story

One sample is 153 × 4 × 512 × 512 × float32 ≈ 640 MB. The DataLoader queue holds workers × prefetch × batch_size samples, so 12 workers × 2 prefetch × batch 8 is already ~123 GB of host RAM in flight. --host_mem_budget_gb (via lakevision/data/loader_plan.py) sizes workers against your SLURM --mem instead of guessing; persistent_workers is deliberately off so train and val workers never coexist. Measured on Sherlock at N=1,175: ~14.5 min/epoch, ~99% of it in the dataloader — decompressing zlib float32 NetCDF is the pipeline's true bottleneck, and the reason a caching rewrite lives on feature/cache-data.

04The model

lakevision/models/classifier.py::LakeDrainageClassifier is a small multi-stream network — 139,925 parameters, deliberately modest for a few thousand training samples. Each input stream is reduced to a fixed-length feature vector; the vectors are concatenated and classified by a tiny MLP. Everything below shows the baseline configuration (RGB + mask, area stream on, cloudy stream off, attention off).

4.1 FrontCNN — per-frame spatial encoder

The FrontCNN (lakevision/models/blocks.py) is a plain 4-layer conv stack with no normalization layers, no residuals — each layer is Conv2d(3×3) → LeakyReLU → MaxPool(2). It treats time as batch: the input [B,T,3,512,512] is reshaped to [B·T,3,512,512], every frame is encoded independently by the same weights, then reshaped back. All temporal reasoning is deferred to the ConvLSTM.

4.2 ConvLSTM — spatiotemporal memory

The heart of the model (lakevision/models/clstm.py, after Shi et al. 2015). A standard LSTM would flatten each frame to a vector and lose all spatial structure; a ConvLSTM keeps hidden state and cell state as feature maps — here [B,32,32,32] — and replaces every matrix multiply with a 3×3 convolution. The gates are computed by one convolution on the concatenation of the current input and the previous hidden state, producing all four gates at once:

Reading the output: the model takes the last timestep's hidden state [B,32,32,32] — the LSTM's summary after having watched the whole window — and collapses space with global average pooling to [B,32]. Alternative readouts (mean/max over time, avg‖max pooling) exist as CV-grid axes but are not the baseline.

4.3 The scalar streams

The area stream is a vanilla nn.LSTM with hidden size 16 over the min-max-normalized water-area curve [B,T,1] → last timestep → [B,16]. It's tiny (1,216 parameters) but potent: "area collapses to zero in three frames" is nearly a drainage classifier on its own, and this stream hands the model that signal directly. The cloudy stream is an identical LSTM over the per-frame usefulness flag (1 = useful, 0 = cloudy) — currently off, pending the cloudy-tile CNN retrain. Optional per-timestep learned weights (learn_area_weights) can sigmoid-gate each frame's scalar before the LSTM.

4.4 Fusion and head

Feature vectors concatenate to [B,48] (32 image + 16 area) and a one-hidden-layer MLP — 48 → 64 → ReLU → dropout 0.3 → 5 — produces logits. No softmax in the model; CrossEntropyLoss applies it during training and inference scripts apply it explicitly.

4.5 Where the parameters live

Two things worth internalizing. First, parameter count is independent of spatial size — the weights are conv kernels, so the ESSD-era 64×64 configuration has the exact same 139,925 parameters as today's 32×32 one, but ~4× the ConvLSTM compute and activation memory. Second, the model contains no normalization layers anywhere — no BatchNorm, no GroupNorm, no LayerNorm. It trains anyway (LeakyReLU + small depth), but this is a live CV-grid axis, and it makes the model unusually sensitive to input scaling — which is exactly why the normalization mismatches in §08 matter.

4.6 Variants you'll see in the code

Vector mode (frontcnn_out_hw=(1,1)): pool the FrontCNN output to 1×1, squeeze, and run a regular nn.LSTM instead of the ConvLSTM — 41,749 parameters, no spatial reasoning through time. A cheap ablation baseline. Attention (attention_type): spatial (CBAM spatial gate), full (CBAM channel + spatial), or arch — a second FrontCNN encodes the mask channel and its features multiply the imagery features, the only configuration in which the mask influences anything. All were off for the ESSD baselines.

05Training

Everything is driven by engine/training/run_training.py, whose argparse defaults are the ESSD baseline — the SLURM scripts beside it stay short on purpose. The recipe:

KnobBaseline valueNotes
LossCrossEntropy, inverse-frequency class weightscomputed on the train split
OptimizerAdam, lr 1e-4 fixed, weight decay 1e-5no scheduler (flag exists for ablations)
Precisionbf16 autocast, on by defaultno GradScaler needed (bf16 = fp32 range)
Batch / epochs / seed8 / 400 / 42bs=8 ≈ 28 GB VRAM on main; bs=32 OOMs a 40 GB A100
Labels--label_mode essd_5classstring labels from GUI CSVs → ints 0–4
Splits--{train,val,test}_ids_filealways pass the committed splits/ files

Three checkpoints stream out per run, all bare state_dicts (the ESSD format — reconstruct the model from config before loading): <stem>.pth at best val loss — this one is reloaded for the final test evaluation — <stem>_bestf1.pth at best val macro-F1, and <stem>_epoch{N}.pth every 5 epochs. Per-epoch metrics go to stdout and, when available, wandb.

A typical launch (Sherlock paths abbreviated):

python3 engine/training/run_training.py \
    --labels_csv labels/labels_CW_2018.csv labels/labels_CW_2019.csv \
    --nc_dir $COMPOSITES_DIR \
    --train_ids_file splits/essd_CW/train_ids.json \
    --val_ids_file   splits/essd_CW/val_ids.json \
    --test_ids_file  splits/essd_CW/test_ids.json \
    --host_mem_budget_gb 325 \
    --save_path models/run_name.pth

Useful switches: --max_lakes N caps every split for smoke tests; --max_train_lakes N is the learning-curve knob (valid because train IDs are nested-stratified); --augment turns on D4 (default random mode — but see §08 before using it); --merge_classes MD LD folds two classes for 4-class ablations; --test_labels_csv switches to cross-year mode.

Reproducing the ESSD baselines

The published runs used the then-default frontcnn_out_hw=(64,64), which silently upsampled the FrontCNN's 32×32 output to 64×64 — 4× ConvLSTM cost for no information gain. Current main removed the default and made upsampling requests raise. Consequence: several docstrings still say "pass (64,64) to reproduce," but on main that now raises ValueError at the first forward. The only faithful way to run or retrain the ESSD configuration is the frozen tag: git checkout essd-2026-submission. Loading an ESSD checkpoint into today's default 32×32 model "works" — same weights, different forward — and will quietly give you different predictions. See docs/PROVENANCE_ESSD.md for tags and the commit behind every number.

06Evaluation & results

The headline metric is macro F1 — the unweighted mean of per-class F1 — because accuracy is inflated by the LD-heavy class balance. run_training.py reports accuracy, macro precision/recall/F1, per-class F1, and a confusion matrix at the end of every run, computed on the held-out test split with the best-val-loss checkpoint. Where the numbers stood at ESSD submission:

BaselineBest val F1Test F1Per-class test F1
Cross-year (train 2019 → test 2018)0.6200.445ND 0.46 · HF 0.47 · MD 0.06 · LD 0.54 · CD 0.70

Two honest readings. The cross-year gap (0.62 val → 0.45 test) is the year-to-year generalization cost, and moulin drainage (MD) is nearly unlearnable at this data scale — it is visually subtle and easily confused with LD. And the learning curve says the models were still improving when walltime ran out:

N train lakes20040060080010001175
Best val macro F10.4980.5290.5670.5680.5640.607

Best-val epochs cluster at 330–400 of 400 — the ESSD baselines are compute-limited, not converged. They are presented as reference points for a dataset paper, not tuned models; the reported numbers are a floor. Squeezing the actual ceiling out of this architecture is the planned cross-validation grid (docs/CV_GRID.md), which is blocked mainly on the dataloader rewrite.

For batch inference, engine/inference/run_inference.py loads a checkpoint, walks a list of lake IDs, and appends per-lake predictions with all five class probabilities to a resumable CSV — flushed row by row so a SLURM kill leaves a valid partial file. Read §08 before trusting its outputs against training-time metrics.

08Sharp edges

Current as of August 2026 — each of these was verified against the code, and several are the kind that fail silently. Check the claudiary for anything that changed since.

  1. The mask channel is loaded, then discarded. Unless attention_type='arch', the mask is split off in forward() and never touches the computation — measured zero effect on logits. Paper text saying the model uses "imagery + water_area + mask" describes the plumbing, not the math. (--mask_as_channel exists on the branch.)
  2. ESSD checkpoints don't reproduce on main. Trained at 64×64; main's model refuses to upsample (raises) and its default runs 32×32 — into which an ESSD checkpoint loads without error and predicts differently. Use the essd-2026-submission tag for anything ESSD-faithful; that is the tag's whole job.
  3. Cloudy-flag polarity trap. cloudy_seq_* is 1 = useful. The stack-level eo_cloud_cover is scene-level and inverted (1 = cloudy) — never substitute one for the other. The missing-data fallback is ones ("all frames useful") everywhere.
  4. Band flags are trust-based. --use_swir22 isn't wired in the training CLI at all, and nothing on main asserts dataset channels match model channels — historically extra channels were silently dropped. The assert lives on feature/cache-data; re-land it before running the spectral-bands axis.
  5. The README is only half-trustworthy. Its architecture tables were corrected in August 2026, but the intro/installation sections are still placeholders. Precedence for truth: code → docs/ → claudiary → README.

Fixed in August 2026 — history that still matters

These were live bugs until this audit; you'll meet their fingerprints in old outputs.

  • Inference used to skip training's normalization. run_inference.py and predict_lakes.py (and the talk/comparison notebooks they mirror) fed raw water area where training min-maxed it per sample, and divided imagery by 10,000 without the [0,1] clip. Both scripts now mirror LakeDataset exactly — which means prediction CSVs generated before the fix are not comparable to training-time metrics or to new CSVs. Regenerate before reusing.
  • NaN in the area series is now guarded end to end. Loaders raise on a composite water_area containing any NaN and fill SDR p_water (raising only on an all-NaN season); the writers refuse to emit an all-NaN series, and the legacy preprocessor no longer hardcodes a 2019 date window. Before the guards, one NaN silently turned the whole area stream — and the loss — into NaN.
  • --augment random mode drew one symmetry per lake per run (set_epoch was never called). run_training.py now advances the seeded draw each epoch. ESSD's expand-mode runs were never affected.
  • predict_lakes.py was dead — it fed area_seq as [1,T], which ScalarLSTM rejects. Fixed, and its normalization now matches training.
  • seq_len is pinned to 153 in the training CLI (the full melt season) — deliberately not a CV-grid axis. If it's ever unpinned: the window math yields 2·(seq_len//2)+1 frames, so keep it odd, and files shorter than seq_len still crash the default collate at batch > 1.
